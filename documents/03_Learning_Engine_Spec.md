# Learning Engine Specification

## 1. Назначение

Движок решает каждый день три вопроса:

1. Что пользователь должен вспомнить?
2. Что он должен сегодня уметь применить?
3. Что больше всего ограничивает следующий уровень readiness?

## 2. Типы учебной активности

- Recall — активное воспроизведение.
- Explain — объяснение своими словами.
- Apply — решение задачи.
- Debug — поиск причины ошибки.
- Build — изменение реального SaaS.
- Transfer — применение знания в незнакомом контексте.
- Interview — ответ в условиях собеседования.

## 3. Модель повторения

MVP использует параметризуемую интервальную модель, а не жестко зашитые даты.

Начальные интервалы: 1, 3, 7, 14, 30, 60 дней.

Каждая попытка дает качество:

- 0 — не вспомнил;
- 1 — частично;
- 2 — правильно с подсказкой;
- 3 — правильно без подсказки;
- 4 — правильно + применил/объяснил.

Правило MVP:

- 0–1: интервал сокращается;
- 2: повтор через короткий интервал;
- 3: интервал увеличивается;
- 4: интервал увеличивается сильнее, но тема возвращается для долговременного контроля.

Точная формула должна быть отдельным модулем `scheduler`, чтобы ее можно было заменить на FSRS-подобную модель без изменения остальной системы.

## 4. Алгоритм выбора дневных заданий

Вес кандидата:

`Priority = ForgettingRisk * Weakness * Importance * Staleness`

Где:

- ForgettingRisk — риск забывания;
- Weakness — слабость навыка;
- Importance — важность для target role;
- Staleness — время с последнего подтверждения.

Дополнительно:

`CriticalWeakness` получает высокий коэффициент и не может быть вытеснен легкими задачами.

## 5. Ограничение нагрузки

В дневной сессии по умолчанию:

- 5–10 recall items;
- 1 main coding task;
- 1 project/explanation task;
- 1 короткий reflection.

Количество должно адаптироваться по фактическому выполнению и результатам пользователя.

## 6. Правило ошибки

Любая ошибка классифицируется минимум как:

- knowledge gap;
- memory lapse;
- application gap;
- debugging gap;
- communication gap;
- AI dependency;
- careless error.

Для каждого типа есть remediation action.

## 7. Защита от иллюзии знания

Тема не считается `verified`, если пользователь только ответил на теоретический вопрос. Нужна минимум одна независимая application evidence.

Критичные темы требуют двух независимых подтверждений в разное время.

## 8. Weekly assessment

Каждую неделю:

- 20 theoretical retrieval questions;
- 2 coding tasks;
- 1 debugging task;
- 1 project explanation;
- 1 architecture question.

Контроль не использует AI-помощь. При необходимости система может оценить ответ AI, но модель не помогает формировать решение.
